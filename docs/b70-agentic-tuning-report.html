Making a 27B Agentic Model Practical on an Intel Arc Pro B70

Repeated profiling, configuration tuning, and real coding-agent evaluations across Pi, Pi-Wiggum, and OpenCode.
Bottom line: the B70 became a credible local agentic coding machine. The winning Qwen3.8 profile combines f16 KV cache, one-token MTP speculation, a long reasoning ceiling, and zero presence penalty. It recovered deep-context speed and passed every behavioral check we applied.

Executive summary

The original goal was to make a large local model useful for agentic coding on a Battlemage B70 rather than merely impressive in a short benchmark. The work proceeded as a loop: update llama.cpp, rebuild against Intel oneAPI, measure context-depth behavior, test speculative decoding, test sampling choices, verify tool and vision paths, then run the same coding task through multiple agents.

The central finding was that the slow path was not the model’s raw compute. It was the SYCL quantized KV-cache flash-attention path as context grew. On Qwen3.8, q8 KV decode dropped from 26.6 t/s at an empty context to 15.5 t/s around 16K tokens. Changing only the KV cache to f16 raised that deep-context result to 22.2 t/s; adding one-token MTP reached 33.8 t/s with 86% acceptance.

The final recommendation is deliberately profile-based: use qwen3.8-27b-think for 128K reasoning-heavy agent work, qwen3.8-27b-mtp when 256K context matters more, and qwen3.6-35b-a3b UD-Q4_K_S as the balanced general-purpose Qwen option.

Important memory trade-off: the Qwen3.8 hybrid model has only 16 full-attention layers, but f16 KV still costs about 64 KiB per token. That is roughly 8 GiB at 128K and 16 GiB at 256K. The B70 can afford 128K f16 KV beside the weights, but 256K f16 KV is not practical.

Best operating procedure

  1. Keep llama-swap.service as the single model switchboard and expose the OpenAI-compatible endpoint at http://127.0.0.1:8080/v1.
  2. For Pi or OpenCode agentic coding, select qwen3.8-27b-think. Keep the client context limit aligned with the server: 131,072 for this profile. OpenCode evaluation required an explicit --lms-context-length 131072 override.
  3. Keep --ctk f16 --ctv f16, flash attention, --parallel 1, MTP draft length 1, reasoning budget 8192, and presence penalty 0.
  4. Use request-level reasoning_effort=low for routine coding and medium/xhigh only when the task justifies longer reasoning. Avoid none as a shortcut.
  5. Use qwen3.8-27b-mtp for a real 256K-context requirement, accepting the q8-KV deep-context penalty. Use the non-MTP alias when speculative behavior is undesirable.
  6. Keep the Unsloth Qwen3.6 UD quant for balanced general-purpose work, and use smaller Gemma for quick transformations. Agents-A1 remains the high-throughput long-horizon alternative; Muse Glimmer remains useful for multimodal ATEM tool work.
  7. After changing a model alias or context, run ~/Code/intel/bin/llm-swap configure so Pi and OpenCode receive the same model list, modalities, context, and output limits.

What to keep, what to avoid

Keep

  • Current llama.cpp refresh and IntelLLVM/SYCL build.
  • Level Zero, oneDNN, FP16 kernels, host-memory fallback, flash attention.
  • JIT device compilation with GGML_SYCL_DEVICE_ARCH unset.
  • One-token MTP for Qwen3.8; f16 KV for deep-context agents.
  • Prompt caching with one serialized agent slot.

Avoid or treat as experimental

  • Qwen3.8 q8 KV for deep 128K reasoning when latency matters.
  • ngram-mod on this SYCL backend.
  • Nemotron MTP as a default; it regressed and could stall on longer work.
  • AOT BMG architecture flags that remove the >4 GB buffer path.
  • Removing the DPC++ compiler/shared development packages if rebuilds are expected. Eclipse plugins and some CCL/debugger extras are not runtime requirements, but the compiler/toolchain is.

Limitations and interpretation

  • The before/after runs compare the older qwen3.8-27b profile with the tuned qwen3.8-27b-think profile. They are practical end-to-end comparisons, not single-variable laboratory controls.
  • The Pi baseline’s exact wall time was not persisted, and the long-run harness did not retain separate prompt-processing and generation rates. Short controlled llama-server measurements remain the authoritative throughput data.
  • The automated browser probes establish load, animation, canvas, and error-free execution; they do not fully judge visual or behavioral quality. The human scores supplied for this report are therefore valuable complementary evidence.
  • The first OpenCode run was invalid for apples-to-apples comparison because it advertised 32K context. It was stopped, checkpointed, and excluded from the final performance table.
Conclusion: profiling changed the recommendation from “run the largest model that fits” to “match cache precision and context to the workload.” On this hardware, that distinction is worth the difference between a model that feels sluggish at depth and one that can complete a long agentic coding task reliably.
